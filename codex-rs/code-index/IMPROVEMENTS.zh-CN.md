# 本地代码索引：能力与效果报告

## 结论

本次为 Codex 增加了可选的本地代码索引与混合检索能力，解决了大仓库中
“只能逐文件搜索、上下文发现依赖模型反复浏览、增量更新成本不可控”的问题。
英文基准报告见 [`PERFORMANCE.md`](PERFORMANCE.md)。

核心结果：

- 20,000 个源码文件、160,000 个 AST chunks 的仓库可在约 10.0 秒内完成全量索引。
- 60 次混合查询的整体 P50 为 **5.011 ms**，P95 为 **12.016 ms**，满足 P95 小于 200 ms 的验收门槛。
- 单文件增量更新 P50 为 **164.804 ms**，P95 为 **167.041 ms**，满足 P95 小于 2 秒的验收门槛。
- 全量索引耗时约为单文件增量更新的 **60.40 倍**。该数字只描述索引更新成本差异，不代表检索速度提升。
- 索引及检索过程中的峰值 RSS 为 **32.547 MiB**。
- 同一混合查询集下，索引检索相对无索引基线的 **P50 快 11.81–15.04 倍**、
  **P95 快 5.77–6.44 倍**，60 次查询总耗时快 **13.66–13.75 倍**。
- 自然语言查询 P50 为 **0.980 ms**，P95 为 **18.858 ms**；整体 P95 不再由约 150 ms 的自然语言延迟决定。
- Agent turn 会自动注入有 token 预算的代码上下文；索引缺失或不可读时会回退到 ignore-aware 文件搜索。
- 敏感文件、隐藏文件、生成文件、二进制文件及被 `.codexignore` 排除的文件不会进入索引或回退结果。

本报告的索引/无索引对照使用同一数据集、同一机器和同一查询集。无索引侧同时测量
两种基线：Codex 索引不可用时实际使用的 ignore-aware 文件名回退搜索，以及模拟
`rg` 的全量文件内容扫描。不同查询类型的差异很大，因此不把某一个倍数当作所有
查询的通用加速比。

## 能力提升

| 场景 | 引入本地代码索引前 | 引入本地代码索引后 |
| --- | --- | --- |
| 符号定位 | 依赖文本搜索或模型逐文件浏览，结果容易受命名相似度影响 | FTS、trigram、精确符号和可选向量检索并行执行，再通过 weighted RRF 融合排名 |
| 自然语言检索 | 需要多轮文件浏览和关键词试探 | 按 term 选择性裁剪 FTS/trigram 后端，再返回带路径、行号、符号和上下文的代码块 |
| 路径检索 | 文件名和关键词通常只能分别搜索 | 路径意图单独识别，明确文件路径可获得更高排名 |
| 检索结果可用性 | 原始命中可能零散、重复或超出上下文窗口 | 合并相邻 chunks、补充邻近上下文，并按 token budget 裁剪 |
| 大仓库刷新 | 重新扫描和重建成本高 | 内容哈希比较后只更新变化文件，支持 debounce watcher |
| Agent 上下文 | 需要模型自行决定读哪些文件 | turn 开始前自动注入有界代码上下文，并提供无索引回退 |
| 隐私边界 | 搜索范围容易意外包含敏感或忽略文件 | 索引、回退搜索和增量更新共用同一套过滤策略 |
| 外部依赖 | 若要向量检索通常需要独立服务 | 默认仅使用本地 SQLite；向量检索可选，未配置时不发起网络请求 |

## 性能测试

### 环境

| 项目 | 值 |
| --- | --- |
| CPU | AMD Ryzen 7 9700X，8 核 16 线程 |
| 操作系统 | Linux 7.0.0-42-generic x86_64 |
| Rust | rustc / cargo 1.99.1 |
| 构建 | release |

### 数据集与方法

- 使用合成源码仓库，共 **20,000** 个文件。
- 索引生成 **160,000** 个 AST chunks。
- 执行 **60** 次查询：
  - 符号查询 20 次；
  - 路径查询 20 次；
  - 自然语言查询 20 次。
- 查询延迟包含查询分析、后端检索、RRF 融合、上下文合并和 token 裁剪。
- 执行 **3** 次单文件增量更新，统计其 P50/P95。
- 内存数据来自同一基准进程的 RSS 采样。

### 瓶颈定位与优化

早期结果中自然语言查询接近 150 ms，最初容易把原因归到 RRF 融合。对旧查询
逐阶段测量后，实际瓶颈是宽泛 FTS/trigram 查询的排名：

| 阶段 | 旧自然语言查询耗时 |
| --- | ---: |
| FTS/BM25 | 104–107 ms |
| Trigram | 152 ms |
| 精确符号检索 | 0.4–0.6 ms |
| RRF 融合 | 0.09–0.16 ms |
| 去重、上下文合并与裁剪 | < 0.3 ms |

查询中的多个 OR term 几乎命中全部 160,000 个 chunks，导致 FTS5 和 trigram
必须对巨大的 posting list 排序；此时只在外层增加 `LIMIT` 并不能省掉排名成本。
RRF 只处理已经截断到候选上限的结果，因此不是瓶颈。

现在自然语言查询会先做选择性路由：

1. 最多取 8 个查询 term；
2. 查询各 term 的 FTS 文档频率，并按 SQLite `data_version` 失效缓存；
3. 只把命中 chunks 不超过 `max(total_chunks / 20, 64)` 的 term 视为选择性 term；
4. 最多使用 3 个选择性 term 构造精确短语 FTS 查询；
5. 单 token term 通过 FTS5 vocabulary 表做快速文档频率查找；多 token term 仍用精确 MATCH 计数；
6. 只有在至少选中一个真正选择性 term 时才启用 trigram；
7. 如果所有 term 都很常见，只查询其中文档频率最低的一个，避免构造大 OR 查询。

符号和路径查询保持原有的 prefix-FTS + trigram 行为。后端仍会在进入 RRF 前
应用候选上限，所以融合输入始终有界。

FTS5 vocabulary 快路径将同一基准中的自然语言 P95 从 **22.350 ms** 降至
**18.858 ms**。多 token term 不能直接使用单个 token 的文档频率，因为那不能表示
短语共现，所以仍保留精确计数作为正确性回退。

### 查询延迟

| 查询类型 | P50 | P95 |
| --- | ---: | ---: |
| 全部查询 | **5.011 ms** | **12.016 ms** |
| 符号查询 | 5.307 ms | 12.016 ms |
| 路径查询 | 4.978 ms | 5.811 ms |
| 自然语言查询 | **0.980 ms** | **18.858 ms** |

自然语言 P50 低于符号和路径查询，是因为这些基准查询可以快速选中一个高频 term
而不必执行宽泛多后端搜索。P95 较高是因为每个新 term 的首次查询需要支付文档频率
统计成本，后续查询会使用按数据库版本失效的缓存。

在独立 `incremental_benchmark 20000 60 3` 参考运行中，查询 P95 为
**12.159 ms**，自然语言 P95 为 **18.641 ms**，两项均低于 200 ms 验收门槛。

### 索引、更新与资源占用

| 指标 | 实测值 |
| --- | ---: |
| 全量索引耗时 | 10,089 ms |
| 全量索引内部报告耗时 | 10,088 ms |
| 索引 chunks | 160,000 |
| 首次单文件增量更新耗时 | 167 ms |
| 单文件更新文件数 | 1 |
| 单文件更新 chunks | 8 |
| 增量更新 P50 | 164.804 ms |
| 增量更新 P95 | 167.041 ms |
| 全量索引 / 首次单文件增量更新 | 60.40x |
| 索引数据库大小 | 186.766 MiB |
| 索引完成后 RSS | 29.145 MiB |
| 检索后 RSS | 31.199 MiB |
| 进程峰值 RSS | 32.547 MiB |

`60.40x` 的含义是：

```text
全量索引耗时 / 首次单文件增量更新耗时 = 60.40
```

它说明增量更新显著降低了重复索引成本，但不能解释为“检索速度提升了 60 倍”。

## 索引与无索引对照

### 对照方法

在相同的 20,000 文件合成仓库和 60 次查询上连续运行 3 次，取中位数。索引进程在
测量前已经完成全量索引并打开 SQLite 连接；无索引侧每次查询都重新发现文件，不做
跨查询结果缓存。

无索引基线有两类：

1. **无索引回退搜索**：调用当前扩展实际使用的 `fallback_file_search` 等价流程，
   即每次执行 ignore-aware 文件发现、文件名模糊搜索和敏感文件 allowlist 过滤。
2. **无索引全量扫描**：在同样的文件发现和过滤之后，路径查询匹配路径，其他查询
   读取每个文件内容并匹配查询 term，近似 `rg` 式搜索。

### 混合查询结果

连续 3 次运行的中位数：

| 指标 | 索引检索 | 无索引回退搜索 | 无索引全文扫描 |
| --- | ---: | ---: | ---: |
| 全部查询 P50 | **5.011 ms** | 59.192 ms | 75.353 ms |
| 全部查询 P95 | **12.016 ms** | 69.328 ms | 77.347 ms |
| 60 次查询总耗时 | **273.230 ms** | 3,732.366 ms | 3,756.836 ms |
| 空结果次数 | 0 / 60 | 40 / 60 | 0 / 60 |

据此计算：

| 对比 | P50 加速比 | P95 加速比 | 60 次查询总耗时加速比 |
| --- | ---: | ---: | ---: |
| 索引 vs 无索引回退搜索 | **11.81x** | **5.77x** | **13.66x** |
| 索引 vs 无索引全文扫描 | **15.04x** | **6.44x** | **13.75x** |

这里不能只引用 P50：

- P50 的 **11.81–15.04x** 说明典型查询节省了约 54–70 ms。
- P95 的 **5.77–6.44x** 说明尾部延迟也已明显优于无索引基线。
- 混合负载的总耗时快 **13.66–13.75 倍**，而不是只快 1.2 倍左右。
- 无索引回退搜索在 40/60 次查询中返回空结果，不能只按延迟与索引检索比较。

### 按查询类型拆分

| 查询类型 | 索引 P50 / P95 | 回退搜索 P50 / P95 | 全文扫描 P50 / P95 |
| --- | ---: | ---: | ---: |
| 符号 | **5.307 / 12.016 ms** | 67.754 / 70.834 ms | 76.205 / 79.014 ms |
| 路径 | **4.978 / 5.811 ms** | 59.140 / 68.475 ms | 35.808 / 37.291 ms |
| 自然语言 | **0.980 / 18.858 ms** | 58.087 / 68.476 ms | 75.514 / 76.779 ms |

按 P50 计算：

| 查询类型 | 相对回退搜索 | 相对全文扫描 |
| --- | ---: | ---: |
| 符号 | **12.77x** | **14.36x** |
| 路径 | **11.88x** | **7.19x** |
| 自然语言 | **59.27x** | **77.06x** |

按 P95 计算：

| 查询类型 | 相对回退搜索 | 相对全文扫描 |
| --- | ---: | ---: |
| 符号 | **5.89x** | **6.58x** |
| 路径 | **11.78x** | **6.42x** |
| 自然语言 | **3.63x** | **4.07x** |

### 如何解读

- **符号查询**：索引 P50 快 **12.77–14.36 倍**，P95 快 **5.89–6.58 倍**。
- **路径查询**：索引 P50 快 **7.19–11.88 倍**，P95 快 **6.42–11.78 倍**。
- **自然语言查询**：索引 P50 快 **59.27–77.06 倍**，P95 快 **3.63–4.07 倍**。
- 无索引回退搜索虽然 P50 为 59.192 ms，但 40/60 次查询没有返回任何结果；
  它的低延迟不能视为完成了同等质量的检索。
- 自然语言 P95 的主要成本是首次查询的 term 统计，而不是 RRF；缓存命中后查询会
  明显更快。无索引全文扫描只是逐文件 substring 匹配，两者完成的工作并不相同。

如果只需要一个面向混合查询的简短结论，应表述为：

> 在 20,000 文件、60 次混合查询基准中，索引检索的 P50 比无索引搜索快
> 11.81–15.04 倍，P95 快 5.77–6.44 倍，60 次查询总耗时快 13.66–13.75 倍。

这里应保留 P50、P95 和总耗时三个维度，不能只用单一倍数描述所有查询类型。

### 验收结果

| 验收项 | 门槛 | 结果 |
| --- | --- | --- |
| 查询 P95 | < 200 ms | 12.159 ms，通过 |
| 增量更新 P95 | < 2 s | 167.041 ms，通过 |

## Agent 上下文注入效果

启用 `features.code_index` 后，扩展会在每轮用户输入前使用任务文本执行检索。
输出不是整文件内容，而是包含以下信息的内部上下文片段：

- 文件路径；
- 起始和结束行号；
- 命中的符号名；
- 经过合并和预算裁剪的代码内容。

该设计带来三点直接效果：

1. **减少盲目浏览**：模型一开始就能看到与任务相关的实现位置。
2. **控制上下文成本**：注入内容受 `token_budget` 和 `max_results` 限制，不会挤占整个上下文窗口。
3. **平滑降级**：索引不存在、数据库不可读或检索失败时，扩展使用同一过滤策略的文件搜索，而不是让 turn 失败。

相关测试覆盖：

- 启用后能注入目标源码和符号；
- 禁用时不产生任何上下文；
- 索引缺失时回退到文件搜索；
- 回退搜索不泄漏 `.env` 和 `.codexignore` 排除文件；
- 注入内容不超过配置的 token budget。

## 正确性与隐私验证

检索正确性测试覆盖符号、路径和自然语言三类查询，并验证：

- 精确符号排在结果前部；
- 指定路径的文件优先返回；
- 自然语言描述能找到对应实现；
- 相邻 chunks 在返回前合并；
- 返回内容满足 token budget。

隐私与索引边界验证覆盖：

- `.env` 等敏感文件不会出现在索引或回退结果中；
- `.codexignore` 排除的文件不会被索引；
- 隐藏目录、生成文件、二进制文件和超大文件被跳过；
- FTS schema 在已有匹配行时可以正常探测；
- 查询词项数量及单个词项长度有上限，避免超长任务文本生成无界 SQL/FTS 表达式。

## 使用方式

### CLI

```bash
# 全量建立索引
codex index init

# 后台建立索引，避免阻塞当前流程
codex index init --background

# 增量更新
codex index update

# 持续监听文件变化
codex index watch

# 查看索引状态
codex index status

# 直接检索
codex index search "increment_counter"
```

可显式指定仓库路径、数据库路径、并发数和检索预算：

```bash
codex index init /path/to/repo --db .codex/index.sqlite --jobs 8
codex index search "where is retry backoff implemented" --budget 1200 --limit 8
```

### 功能配置

```toml
[features.code_index]
enabled = true
token_budget = 1200
max_results = 8
index_path = ".codex/index.sqlite"
embedding = false
debug = false
```

默认关闭该功能。只有显式启用后，Agent turn 才会注入代码索引上下文。

## 实现要点

- **发现与过滤**：遵循 ignore 规则，过滤隐藏、生成、二进制、超大和敏感文件。
- **AST 分块**：按语言和 tree-sitter 节点切分；解析失败时使用安全 fallback。
- **混合检索**：FTS5、trigram、精确符号和可选向量后端并行读取，使用 weighted RRF 融合。
- **自然语言选路**：按 term 文档频率选择最多 3 个选择性 term；单 token 使用 FTS5 vocabulary 快速统计，所有 term 都常见时只查询最低频 term；trigram 仅在存在选择性 term 时启用。
- **结果整形**：合并相邻 chunks、补充邻近上下文、按 token budget 裁剪。
- **缓存**：查询 embedding 和完整搜索响应用有界 LRU；embedding 使用内容哈希持久缓存。
- **增量更新**：基于内容哈希识别变化文件，以批次事务写入 SQLite。
- **后台与监听**：支持 background indexing 和 debounce watcher。
- **扩展集成**：通过现有 extension registry 接入 turn context，不改变默认关闭行为。

主要实现文件：

- `src/discovery.rs`：索引范围、ignore 规则和敏感文件过滤。
- `src/language.rs`：语言识别与 tree-sitter 节点策略。
- `src/chunker.rs`：AST 语义分块与 fallback。
- `src/store.rs`：SQLite schema、FTS/trigram/symbol/vector 查询。
- `src/indexer.rs`：全量/增量索引、批处理、取消与锁。
- `src/watch.rs`：debounced watcher。
- `src/embedding.rs`：可选 embedding provider 与内容哈希缓存。
- `src/search.rs`：查询分析、并行后端、RRF、上下文与预算控制。
- `src/cli.rs`：`codex index` 子命令。
- `../ext/code-index/src/extension.rs`：Agent turn 上下文注入与回退搜索。
- `examples/incremental_benchmark.rs`：延迟、增量更新、索引大小和 RSS 基准。

## 复现方式

```bash
cd codex-rs
cargo build -p codex-code-index --release --example incremental_benchmark --locked
target/release/examples/incremental_benchmark 20000 60 3

cargo build -p codex-code-index-extension --release \
```

基准程序在查询 P95 达到 200 ms 或增量更新 P95 达到 2 秒时会失败退出。

## 已知边界

- 当前结果是合成仓库基准，真实仓库的延迟会受语言构成、文件大小、文件系统缓存和查询复杂度影响。
- 自然语言查询的 P95 仍高于符号和路径查询。单 token 已使用 FTS5 vocabulary，
  多 token / 短语 term 首次查询仍需要精确 MATCH 计数；后续可增加持久化 term-frequency 摘要。
- 向量检索当前是可选项，使用 SQLite 精确扫描；未引入 ANN 索引，不适合超大规模向量集合。
- 没有常驻索引服务，后台索引完成前仍可能处于部分索引状态。
- 仓库中既有 `codex-config`/core 测试存在与本功能无关的 `ConfigServer`、`config_server`
  字段及辅助函数编译问题；本功能涉及的 crate 测试、检查、clippy 和格式化均通过。

## 总结

该实现把代码检索从“依赖模型逐文件浏览”提升为“本地、可增量、带隐私边界的混合检索”。
在当前 20,000 文件基准中，查询 P95 控制在 12 ms 左右，增量更新控制在 167 ms 左右，
峰值内存约 33 MiB，同时保持默认关闭、默认不联网和无常驻服务的设计。
